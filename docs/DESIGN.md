# J Mercury subnet — design (v1 draft)

Status: **draft for discussion**. Nothing here is registered on chain yet. Numbers marked *(initial)* are starting
values to be tuned on testnet, not promises.

## 1. What the subnet produces

Local service businesses (landscapers, roofers, HVAC, plumbers, dentists, remodelers, med-spas, commercial
contractors) are found by word of mouth and then looked up online. Most of them need the same thing: a clear,
phone-first site whose facts (name, phone, hours, service area) are right.

The subnet turns that into a repeatable task: **given a business brief, build the best phone-first website for it.**
Validators send briefs, miners return finished static sites, validators score them with public rules.

v1 is **frontend only**. Backend work (lead forms, booking, review requests) is a later, separate challenge
(section 9), because it needs a different kind of scoring.

## 2. The task

### 2.1 Brief (validator → miner)

A JSON object. Every brief in v1 is **synthetic**: generated by the validator from a random seed, so it cannot be
looked up or precomputed.

| field | example | notes |
|---|---|---|
| `task_id` | random hex | |
| `trade` | `roofing` | one of: `lawn`, `roofing`, `hvac`, `plumbing`, `dental`, `remodeling`, `aesthetics`, `commercial` |
| `name` | "Ridgeline Roofing Co." | fictional |
| `city`, `state` | "Dayton", "OH" | real US places |
| `service_area` | ["Kettering", "Centerville", …] | |
| `phone` | "(937) 555-0142" | always in the fictional 555-01XX range |
| `email` | "office@ridgeline.example" | `.example` domain |
| `address` | street address, or `null` | `null` = service-area business that does not publish an address |
| `hours` | `{"mon": ["08:00","17:00"], …, "sun": null}` | `null` = closed |
| `services` | 3–8 items, each `{name, detail}` | |
| `facts` | e.g. `{"founded": 2009, "license": "OH-RC-48213", "emergency": true}` | only these may be claimed |
| `owner_notes` | free text, 1–3 sentences in the owner's voice | tone and priorities |
| `required` | `["call", "services", "area", "hours", "about"]` | sections the page must have |

### 2.2 Site (miner → validator)

A zip bundle, base64 in the response:

- `index.html` at the root (v1 is a single page), plus local CSS, images and fonts.
- Limits *(initial)*: ≤ 2 MB zipped, ≤ 5 MB unzipped, ≤ 40 files. Allowed types: `.html .css .png .jpg .jpeg
  .webp .avif .svg .woff2 .ico .txt .xml`.
- **No JavaScript** in v1: no `<script>` (the one exception is `<script type="application/ld+json">` for structured
  data, with no `src`), no `on*=` attributes, no `javascript:` URLs, no `<iframe>/<object>/<embed>/<base>`, no meta
  refresh, no scripts or external references inside SVG. A local business page does not need JavaScript, and forbidding it
  removes a whole class of tricks (detecting the validator's browser and showing it something else).
- **No external resources**: every image, stylesheet and font must be inside the bundle. `data:` URLs count as
  external (put the file in the bundle instead). Ordinary links (`tel:`,
  `mailto:`, `sms:`, an `https:` link to a map) are fine. Validators render with the network switched off.

Timeout *(initial)*: 180 s per brief.

## 3. Scoring

Each sampled miner's site goes through three layers. A site that fails any gate scores **0** for that task.

### 3.1 Gates (deterministic, pass/fail)

1. **Bundle**: the zip opens safely (no path escapes, no links), respects the limits and types, has `index.html`.
2. **No script, no external resources** (section 2.2).
3. **Facts are exact** — this is the promise J Mercury makes to its customers, so it is a gate, not a preference:
   - the business name and the phone number are in the visible text;
   - there is a `tel:` link with the brief's phone digits;
   - "visible" means the rendered text at 390 px: text hidden with CSS does not count;
   - every opening and closing time in the brief appears in the visible text (accepted formats: `8:00 AM`, `8am`,
     `8 a.m.`, `08:00`);
   - a schema.org JSON-LD block of type `LocalBusiness` or a fitting subtype, whose `name`, `telephone` and
     `openingHoursSpecification` equal the brief.
4. **No fake social proof in structured data**: no `AggregateRating` or `Review` in JSON-LD (the brief has none to
   give).

### 3.2 Measured quality (deterministic within noise)

Rendered in headless Chromium, mobile viewport 390 × 844, network off, served by a local static server:

| part | weight *(initial)* |
|---|---|
| Lighthouse mobile — Performance | 0.20 |
| Lighthouse — Accessibility | 0.25 |
| Lighthouse — Best Practices | 0.10 |
| Lighthouse — SEO (on-page checks only, see the note below) | 0.15 |
| No horizontal scrolling at 390 px (a page without a viewport meta tag fails this) | 0.10 |
| A visible call link (`tel:`, with the brief's digits) inside the first 390 × 844 screen | 0.20 |

`M` = weighted sum in [0, 1]. Lighthouse performance is noisy, so each site is measured 3 times and the median is
used. Lighthouse 13.6 is pinned (Node.js ≥ 22.19).

`M` is the groundwork, not the tie-breaker: a lean, well-built page reaches 1.0 (the example site in `examples/`
does), so among good sites the judged part decides.

Note on "SEO": a round cannot measure real search ranking. Lighthouse 13.6's SEO score covers crawlability, title,
meta description, status code, link text, crawlable anchors, robots.txt, image alt text, hreflang and canonical; that
on-page groundwork is all the design claims to measure. Structured data is checked by gate 3 instead.

### 3.3 Judged quality (LLM, pairwise)

All miners sampled in a round get **the same brief**. Every pair of gate-passing sites is shown to a vision LLM:

- inputs: the brief, and for each site a 390 × 844 first-screen screenshot, a full-page mobile screenshot, a
  1280 × 800 desktop first-screen screenshot, and the page's visible text;
- the rubric is public: [`RUBRIC.md`](RUBRIC.md). The judge prompt is the specification — miners should read it.
- each pair is judged **twice with the order swapped**; a win counts only if both orders agree, otherwise it is a tie.
  A judge reply that fails or does not match the format also counts as a tie.

`J` = (wins + 0.5 × ties) / comparisons, in [0, 1]. A site that is the only one left to judge gets 0.5.

**Invented claims**: a claim not in the brief (testimonials, star ratings, awards, prices, "since 1985",
certifications, guarantees) is *confirmed* in a pair when both orders flag it. A site whose invented claims are
confirmed in **at least half of its pairs** scores **0** for the task. (One adverse pair out of seven is a single judge
roll, not a finding; requiring half keeps the penalty for real fabrication without making honest sites gamble.) Real businesses get
into trouble for invented reviews and credentials; the subnet must never teach miners that inventing them pays.

All validators use **one fixed judge model** set in the validator config, so their weights can agree. Which model is
chosen on testnet by measuring how often it agrees with itself on repeated, identical comparisons.

### 3.4 Task score and weights

```
task score = 0                       if any gate fails or invented claims are confirmed
           = 0.4 * M + 0.6 * J       otherwise            (initial weights)
```

Per miner, the validator keeps an exponential moving average of task scores (α = 0.1 *(initial)*) and sets weights
proportional to it. Miners not sampled in a round keep their average.

## 4. Copying and collusion

- Briefs are generated fresh each round, per validator, from a random seed; there is nothing to look up.
- **Duplicates within a round**: if two miners return sites with the same normalised visible text, only the earliest
  response keeps its score; the others score 0. This is on purpose even when only the images differ: every miner in a
  round gets the same brief, and identical wording means the text was shared.
- Near-duplicate detection (same structure, small text edits) is planned for v2 once there is real data on what
  honest diversity looks like.

## 5. Round flow (validator)

1. Generate a brief from a fresh seed.
2. Sample K miners *(initial K = 8)* and send them the brief.
3. Unpack and gate each bundle; render the passing ones (gates, Lighthouse ×3, viewport checks, screenshots).
4. Pairwise judging among passing sites: K(K−1)/2 pairs × 2 orders (56 calls at K = 8).
5. Task scores → moving averages → `set_weights` on the usual cadence.
6. Write a round record (brief, bundle hashes, every gate result, measured parts, every judge verdict) so anyone can
   see why a score was given.

### Transport

bittensor 11 has no axon, dendrite or synapse. Miners run their own small HTTP endpoint and publish it on chain with
the `ServeAxon` intent. The validator POSTs a `SiteTask` (the brief as JSON, `jmercury/protocol.py`) to
`/v1/site-task`, signed with `bittensor.http_auth` (btauth/1): the signature covers the method, path, body hash, a
nanosecond nonce, the validator hotkey and the receiving miner hotkey. The miner checks the receiver binding,
freshness (10 s), the signature and replay, and answers only validators it accepts. Its answer (the brief echoed
back, `bundle_b64`, `miner_version`) is signed by the miner hotkey for that validator and bound to the request's
nonce, so the validator can prove which hotkey sent which bundle and an old answer cannot be replayed to a new
request. A validator waits at most 180 s for the whole exchange and reads at most the size a 2 MB bundle can have;
a missing, late, oversized, unsigned or wrongly signed answer scores 0 for that round. Validator side:
`jmercury/validator/client.py`; reference miner side: `jmercury/miner/server.py`.

## 6. Running the scorer without the chain

The repository ships the validator's scorer, so miners can test before mining:

```
python -m jmercury.brief --seed 42 > brief.json                                    # a sample brief
python -m jmercury.validator.score --brief brief.json --site ./my-site/            # gates + measured
python -m jmercury.validator.score --brief brief.json --site ./a/ --vs ./b/ --judge # plus one pairwise judgement
python -m jmercury.miner.generate --brief brief.json --out ./my-site/              # the reference miner
```

## 7. What validators need

Python 3.10+, Chromium (via Playwright) with its system libraries and fonts, Node.js ≥ 22.19 with Lighthouse 13.6
(`npm ci`), Docker recommended for isolated rendering, and an [OpenRouter](https://openrouter.ai/) API key for the
judge (`OPENROUTER_API_KEY`). No GPU. Scoring one site (render + 3 Lighthouse runs) takes about 30 s, almost all of
it Lighthouse.

The judge goes through OpenRouter's OpenAI-compatible chat API, so every validator can reach the same model under
the same slug; the slug is set in `JM_JUDGE_MODEL` and has no default until it is chosen (section 3.3). Calls use
temperature 0. OpenRouter may route one model slug to different upstream providers; the round record lists which
model and provider pairs answered the round's calls. The reference miner uses OpenRouter too, but any way of producing
the bundle is allowed: the validator only sees the bundle.

## 8. Known limits of v1

- Hours in the visible text are checked by time tokens, not by full day-by-day parsing; the JSON-LD check is the
  exact one, and the judge rubric also asks about fact consistency.
- Single page only; photos are whatever the miner puts in the bundle.
- An LLM judge has noise. Its repeat-agreement is measured before the weights above are fixed.
- Hidden-text checks cover the common CSS tricks (display, visibility, zero size, clipping, off-screen, …); text in
  the same colour as its background is not detected by the gate and is left to the judge.
- The full-page phone screenshot draws bars fixed to the screen (for example a sticky call bar) where they sit on the
  first screen, so they can appear over the middle of the image; the judge is told this.

## 9. Roadmap (subject to discussion)

- **v2 — real work**: multi-page sites; a shared licensed photo set per trade; **edit tasks** ("change the Saturday
  hours", "add a service") that check the change is made and nothing else breaks — that is the "ongoing care" part of
  the business; real customer briefs, only with the owner's consent and only facts the business already publishes,
  with the winning site reviewed by a person before delivery.
- **v3 — backend, as a separate challenge**: lead form to email, booking, review requests, each with its own
  measurable checks.

## 10. Open questions for the community

1. Is K = 8 per round with full pairwise judging the right cost/coverage trade-off, or should judging be against a
   fixed reference site per brief?
2. Which judge model: open-weights (anyone can reproduce) or hosted (stronger, but a single provider)?
3. Should the measured part weigh more than the judged part early on, while the judge's noise is unknown?
